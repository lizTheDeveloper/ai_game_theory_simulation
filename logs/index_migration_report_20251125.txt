RATIONALE FOR NON-CONVERSION
=============================

1. Domain-specific relationship searches:
   - Coalition membership requires checking if BOTH agents are in memberIds array
   - Trust relationships are bidirectional or directed pairs, not simple ID lookups
   - These would require complex composite keys or bidirectional maps

2. Static registry arrays:
   - Government actions, AI actions: Small static arrays (~10-20 items)
   - Tech tree definitions: Static metadata, rarely searched
   - Building indices for these would add complexity without meaningful performance gain

3. Regional/sub-system arrays:
   - Regional deployment, nitrogen management: Per-region arrays (small)
   - Tipping elements: Small array (~10 elements)
   - Treaties: Small array (~5 treaties max)

4. Technology tree special case:
   - PlayerDecisionPhase searches state.technologyTree (full tech metadata)
   - Existing unlockedTech index only covers unlocked status checks
   - Would need separate index for full tech metadata lookup
