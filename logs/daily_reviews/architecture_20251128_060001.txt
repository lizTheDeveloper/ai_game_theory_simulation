### 2. STATE PROPAGATION

**Status: ⚠️ 1 MEDIUM ISSUE**

**MEDIUM-1: Dual Biodiversity Decline Mechanisms**

Location: `PlanetaryBoundariesPhase.ts:143-182` AND `environmental.ts:308-387`

**Issue:** Biodiversity decline is now implemented in TWO places:
1. `PlanetaryBoundariesPhase.execute()` - applies decay multiplier or mechanistic model
2. `updateEnvironmentalAccumulation()` - also has biodiversity decline logic

**Root cause:** The HIGH-8 fix added biodiversity decline to `PlanetaryBoundariesPhase` because "no phase was applying monthly biodiversity decline." However, `environmental.ts` already had this logic, but `updateEnvironmentalAccumulation()` is NOT called as a phase.

**Impact:** Currently safe because:
- Historical mode uses multiplicative decay (0.998899) in PlanetaryBoundariesPhase
- environmental.ts code may be dead code for historical mode
- Both use similar WWF LPI empirical rates

**Risk:** If both paths execute in projection mode, biodiversity could decline ~2x too fast.

**Recommendation:** Audit whether `updateEnvironmentalAccumulation()` is called from any phase. If yes, remove duplicate biodiversity logic. If no, consider moving all environmental accumulation logic into a dedicated phase.

### 4. COMPLEXITY / MAINTAINABILITY

**Status: ⚠️ 2 MEDIUM ISSUES**

**MEDIUM-2: Dynamic require() Pattern Proliferation**

Found 50+ instances of dynamic `require()` in simulation code. Examples:
- `regionalPopulations.ts:470,513,640` - imports from BaselineMortalityPhase
- `planetaryBoundaries.ts` - 11 dynamic requires
- `organizationManagement.ts` - 14 dynamic requires
- `outcomes.ts` - 6 dynamic requires

**Issues with this pattern:**
1. Breaks static analysis and tree-shaking
2. Circular dependency risk (though none detected currently)
3. Runtime import overhead (minor but non-zero)
4. Makes dependency graph opaque

**Root cause:** Appears to be used to avoid circular imports between tightly coupled modules.

**Recommendation:** For next major refactor, consider:
- Extracting shared types/interfaces to dedicated modules
- Using dependency injection pattern for cross-phase communication
- Creating a central "shared utilities" module

---

**MEDIUM-3: Historical Mode Guard Duplication**

The unified `isHistoricalModeActive()` is a good improvement, but the historical mode pattern is now checked **73 times** across 20 files:

```
src/simulation/regionalPopulations.ts:12 occurrences
src/simulation/planetaryBoundaries.ts:11 occurrences
src/simulation/geoengineering.ts:5 occurrences
src/simulation/engine/phases/BaselineMortalityPhase.ts:4 occurrences
...and 16 more files
```

**Issue:** Each call site has its own logic for "what to do in historical mode" - some skip entirely, some apply different parameters, some use empirical data.

**Risk:** If historical mode semantics need to change, 73 call sites may need review.

**Recommendation:** Consider a higher-level abstraction:
- Create mode-aware parameter providers: `getDeathRate(state)` that internally handles historical vs projection mode
- Or use a strategy pattern where each phase selects its historical vs projection behavior once at construction
